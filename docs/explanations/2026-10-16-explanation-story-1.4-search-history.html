How Story 1.4's search history works

Scope: commits 3955140..ab56917 (25 commits) on branch taming-the-dragon-10-16-26-techfusedsm, diamante-investments-v2. Generated 2026-10-16.

Before this change, the search box was forgetful: every visit to a stock started with typing its ticker. Story 1.4 gives it a short memory. Every stock card that successfully loads is recorded in a five-item list in localStorage. Focusing an empty search field shows that list, and clicking a row loads the card directly, with no preview list. Making this work cleanly needed one preparatory refactor (a shared persisted-state hook), one small pure function that does most of the real work, and one browser event-ordering trick that is easy to forget.

1. Background

A beginner's mental model of this app (skip if you know React hooks)

The app is a single React page. React components are functions that take data (props) and return what should be on screen. When a component needs to remember something between renders (such as the text typed in a box), it uses state via useState. When something must happen because state changed, such as writing to storage, it uses useEffect, which runs after the render that changed it.

A custom hook is just a function whose name starts with use and that calls other hooks. This codebase uses them heavily to keep components short: the component renders and the hook decides.

localStorage is a small key-value store in the browser that survives page reloads. It stores only strings, so objects are written with JSON.stringify and read back with JSON.parse. Since anyone can edit it in DevTools, what comes back must be checked.

The change touches the search half of the app. Its shape before the story:

  • useStockSearchFlow is the state container for searching. It owns the query text, a debounced copy of it, the preview list, and the loaded stockData (from useStockData).
  • SearchForm renders the input and, below it, either the preview dropdown or a "No matches found" box.
  • Previews only appear once the debounced query has 2 or more characters, 400 ms after the user stops typing.
  • There are three ways to load a card: click a preview, press Enter, or (new) click a history row. All three end in loadStockData(...), which clears stockData to null, fetches, then sets it to the new value.
  • Story 1.3 had already added a persisted watchlist (useWatchlist) with its own copy of the "read JSON from storage, validate, write back on change" logic.
Contract worth remembering

stockData becomes non-null only after a successful load. A typo like INVALID123 leaves it null and sets an error instead. The whole history feature relies on this: it records what loaded, not what was typed.

2. Intuition

Think of the history as a tiny most-recently-used (MRU) list, a deck where every card you look at goes on top. If the card was already in the deck, it moves rather than duplicates. If the deck grows past five, the bottom card falls off.

The second idea is when the list is visible. The search box can now show two different dropdowns, and they must never overlap. The rule is a single boolean:

isOpen = inputIsFocused && query.trim().length < 2 && history has entries

Previews need 2+ characters and history needs fewer than 2, so the two dropdowns are kept apart by the same threshold (now one shared constant, MIN_PREVIEW_QUERY_LENGTH).

Before: revisiting AAPL

  1. Type AA…
  2. Wait 400 ms for previews
  3. Click the AAPL preview
  4. Card loads

After: revisiting AAPL

  1. Focus the empty input
  2. Click AAPL under "Recent searches"
  3. Card loads; no preview list ever renders

Note that the history stores only { symbol, companyName }, never a price. Clicking a row always fetches a fresh quote, so the dropdown can't show a stale number.

3. Code

The changes group naturally into four layers, presented here in dependency order: shared storage plumbing, pure history logic, the persisted hook, and the UI wiring.

3.1 Make the change easy: shared storage helpers

The first commit (032652c) added no feature. It took the watchlist's persistence logic and split it into reusable parts, so the history wouldn't need a near-copy of it. That was a real constraint, since the repo's duplication gate (jscpd, max 5%) runs on every commit.

export function useLocalStorageState<T>(key: string, parse: (raw: string | null) => T) {
  const [value, setValue] = useState<T>(() => parse(localStorage.getItem(key)));
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);
  return [value, setValue];
}
src/hooks/useLocalStorageState.ts:4

Two details matter here. The initial read is lazy (a function passed to useState), so storage is read once per mount, not on every render. And the write happens in an effect, after React commits the new state, rather than inline in a setter. This avoids writing a value the render later replaces.

export function parseStoredItems<T>(raw: string | null, guard: (value: unknown) => value is T): T[] {
  if (!raw) return [];
  try {
    const parsed = JSON.parse(raw) as unknown;
    if (!isRecord(parsed) || !Array.isArray(parsed.items)) return [];
    return parsed.items.filter(guard);
  } catch {
    return [];
  }
}
src/utils/storage.ts:9

Both stores use the same envelope, { "items": [...] }. The caller supplies a type guard that decides which rows are valid. Bad JSON becomes an empty list; individually bad rows are dropped while good ones survive. Later refactor commits also moved symbol comparison into src/utils/symbols.ts (normalizeSymbol, withoutSymbol, hasSymbol), now shared by both features.

3.2 The pure core: recordSearch

export const SEARCH_HISTORY_LIMIT = 5;

export function recordSearch(entries: SearchHistoryEntry[], entry: SearchHistoryEntry): SearchHistoryEntry[] {
  const symbol = normalizeSymbol(entry.symbol);
  return [{ ...entry, symbol }, ...withoutSymbol(entries, symbol)].slice(0, SEARCH_HISTORY_LIMIT);
}
src/utils/searchHistory.ts:8

All three acceptance rules (newest first, no duplicates, cap at five) live in this one line, and each was driven by its own unit test (src/utils/searchHistory.test.ts:8, :12, :16). Order matters: removing the old copy before slicing means a repeat search never pushes out an innocent fifth entry.

Invariant

After any recordSearch, the list has at most 5 entries, symbols are upper-case, and no symbol appears twice. Symbol comparison ignores case and surrounding whitespace.

The same file holds toSearchHistoryEntry (keeps only symbol and company name) and isSearchHistoryEntry, the guard that requires both fields to be strings (src/utils/searchHistory.ts:17).

3.3 The persisted hook: useSearchHistory

const STORAGE_KEY = 'diamante.searchHistory.v1';

export function useSearchHistory(): SearchHistory {
  const [state, setState] = useLocalStorageState(STORAGE_KEY, parseSearchHistoryState);
  const record = useCallback(
    (stock: StockData): void => {
      setState((current) => ({ items: recordSearch(current.items, toSearchHistoryEntry(stock)) }));
    },
    [setState]
  );
  return { entries: state.items, record };
}
src/hooks/useSearchHistory.ts:23

Two choices here work together. The functional update (setState(current => …)) means record never reads a stale copy of the list. And because record doesn't close over the list, useCallback can keep it stable, the same function on every render. That stability matters in the next step, where record is an effect dependency.

3.4 Recording: an effect on stockData

export function useRecordedSearchHistory(stockData: StockData | null): SearchHistoryEntry[] {
  const { entries, record } = useSearchHistory();
  useEffect(() => {
    if (stockData) record(stockData);
  }, [stockData, record]);
  return entries;
}
src/components/StockSearch/useRecordedSearchHistory.ts:6

Rather than adding a "record" call to each of the three load paths (preview click, Enter, history click), the code watches the result of every load. One effect covers all paths, including any future ones. The if guard is what keeps failed lookups out: they leave stockData as null.

Why the effect runs once per load (inference from the code)

The effect re-runs when stockData changes identity. Each loadStockData call sets it to null and then to a freshly built object (src/hooks/useStockData.ts:21, :26), so each successful load triggers exactly one record. Since record is stable, it never triggers an extra run on its own. If record were recreated every render, the effect would fire on every render; that's harmless here only because recordSearch is idempotent for the top entry, but it would be wasted work.

3.5 Visibility: useSearchHistoryDropdown

const [isFocused, setIsFocused] = useState(false);
const isOpen = isFocused && query.trim().length < MIN_PREVIEW_QUERY_LENGTH && entries.length > 0;

function handleSelect(entry: SearchHistoryEntry): void {
  setIsFocused(false);
  loadSymbol(entry.symbol);
}
src/components/StockSearch/useSearchHistoryDropdown.ts:18

The hook owns only a focus flag; isOpen is derived, never stored, so it can't drift out of sync with the query. It returns one view object, SearchHistoryView, which travels StockSearch → StockSearchPanel → SearchForm as a single history prop instead of five separate ones.

In useStockSearchFlow the wiring is one line plus a tiny loader (src/components/StockSearch/useStockSearchFlow.ts:33, :39):

const history = useSearchHistoryDropdown(useRecordedSearchHistory(stockData), query, loadFromHistory);

function loadFromHistory(symbol: string): void {
  void loadStockData(symbol);
}

Note what loadFromHistory does not do: it doesn't write the symbol into the input. If it did, the debounce effect would see a 2+ character query 400 ms later and open the preview list, breaking the "preview list is not shown" criterion. Passing the symbol as a string means getStockData re-resolves it through a search call and takes the first result (src/services/finnhub/finnhub.ts:43).

3.6 Rendering, and the blur-before-click problem

function keepInputFocused(event: MouseEvent): void {
  event.preventDefault();
}
…
<button type="button" onMouseDown={keepInputFocused} onClick={(): void => onSelect(entry)}>
src/components/SearchHistoryList/SearchHistoryList.tsx:10, :25

This is the subtlest line in the change. When you click a button, the browser fires mousedown, then moves focus (the input gets blur), then fires click. The input's onBlur sets isFocused to false, React re-renders, the list unmounts, and the button is gone before its click arrives. Calling preventDefault() on mousedown stops the focus move, so the list survives long enough to be clicked.

Observed, not theorized

During development, the Scenario 2 acceptance test was run with onSelect wired but without this guard, and it failed; adding the guard made it pass. The user-event library reproduces the real mousedown → blur → click order.

The list itself is a <section aria-labelledby>, which gives it the accessible role region named "Recent searches". The tests find it that way, just as a screen reader would. In SearchForm, the input gains onFocus/onBlur, and the list renders above the preview branch (src/components/SearchForm/SearchForm.tsx:40–45).

4. Edge cases and trade-offs

  • History hides while text is in the box. After any search the ticker stays in the input, so re-focusing shows nothing until it's cleared below 2 characters. This follows the chosen rule but means the backlog's manual test (step 5, "click on the search field again") needs the field cleared first. It's an open product question.
  • Typing one character keeps history open. "A" still shows history (it isn't filtered by the text). At "AA" history hides immediately while previews arrive 400 ms later, so there's a brief moment with no dropdown at all.
  • Escape doesn't close it. Only blur or a selection does. This is out of scope by decision, as is keyboard arrow navigation.
  • Company name can refresh. A history click re-resolves the symbol, and the newly loaded companyName replaces the stored one when it's recorded again.
  • Not covered by a test: failed searches staying out of history. The if (stockData) guard enforces it, but no test pins it.
  • Pre-existing, not from this story: after Enter, previews can reopen ~400 ms later because the debounce effect fires after submit.

5. Glossary

MRU list
Most-recently-used list: newest on top, repeats move up, oldest fall off.
debounce
Waiting until input has been quiet for a fixed time (400 ms here) before acting on it.
effect
A useEffect callback; runs after React commits a render in which its dependencies changed.
functional update
setState(prev => next): computes new state from the latest value, avoiding stale closures.
stale closure
A function that captured an old value of a variable and keeps using it after the value changed.
stable callback
A function that keeps the same identity across renders (via useCallback), so it doesn't retrigger effects.
type guard
A TypeScript function returning value is T; a runtime check that also narrows the type.
envelope
The { items: [...] } wrapper both stores use in localStorage.
lazy initial state
Passing a function to useState so the initial value is computed only on first mount.
blur
The event fired when an element loses focus.
preventDefault
Cancels the browser's default action for an event; on mousedown, that includes moving focus.
region
An ARIA landmark role; a labelled <section> gets it automatically.
jscpd
Copy-paste detector run in the pre-commit hook; fails above 5% duplication.
acceptance test
A test that drives the whole app through the UI to check a user-facing scenario.
mutation check
Deliberately breaking code to confirm a test fails, proving the test actually guards it.
Finnhub
The stock-data API this app calls for search, quotes, profiles, and metrics.
MSW
Mock Service Worker; intercepts network calls in tests and returns canned responses.
